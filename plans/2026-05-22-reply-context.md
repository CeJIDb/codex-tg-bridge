# План: контекст диалога через Telegram reply

**Дата**: 2026-05-22 **Задача**: если пользователь отвечает (Telegram reply) на сообщение бота,
подкладывать предыдущий обмен (вопрос + ответ) в промпт Codex как контекст.

## Зачем именно так

**Hard-rule контекст.** Текущий `codex.mjs` запускает `codex exec --ephemeral` — каждая сессия
изолирована, бот не помнит свои ответы между запусками. План **сознательно** склеивает мультитёрн
поверх ephemeral, держа состояние в bot-процессе. Это компромисс: `--ephemeral` остаётся для самого
codex (sandbox-контракт цел), но bot-слой добавляет один шаг истории. Включается через env
`REPLY_CONTEXT_ENABLED` (default **false** — opt-in), чтобы при необходимости вернуться к строго
stateless поведению.

Сейчас каждый вопрос изолирован: `askCodex(prompt)` получает только текущий текст. Пользователь не
может уточнить предыдущий ответ («а как это соотносится с СОЛАС?», «дай подробнее по пункту 3»), не
повторив весь контекст вручную. UX страдает на сложных навигационных сессиях по графу.

Telegram даёт встроенный механизм: `reply_to_message`. Если бот видит, что юзер отвечает на одно из
**его** прошлых сообщений, можно подтянуть исходный Q+A и добавить в промпт. Никаких новых хранилищ,
никаких команд — пользователь использует обычный жест Telegram-reply.

Альтернативы:

- Полная история чата как контекст — слишком много токенов, мусор от triage и команд.
- Команда `/continue` — лишний шаг, неинтуитивно.
- **Подхват reply на бота как «продолжай этот диалог».** Минимум UI, максимум смысла. Лимит глубины
  — один шаг назад.

Хранение: in-memory `entries: Map<entryId, {question, answer}>` + `lookup: Map<msgId, entryId>`.
**Один entry на ответ** (не на каждый чанк): для плейсхолдера и всех чанков того же ответа
регистрируется один `entryId`. Eviction LRU по числу entries (capacity ~200 диалогов), а не по числу
msgId. Это критично — длинный ответ из 5 чанков иначе занял бы 5 слотов вместо одного.

Переживание рестарта не требуется (после рестарта пользователь просто не получит контекст для старых
сообщений — приемлемо, граф мог тоже измениться).

Обрезка предыдущего ответа в контексте: `prevA` режется по длине, **с сохранением хвоста
«Источники:»** — потому что [src/prompt.mjs](../src/prompt.mjs) явно требует от модели держать
источники в конце ответа, и обрезка сверху-вниз ломает цитирование на уточняющем вопросе.

## Цель

Юзер пишет вопрос → получает ответ. Делает reply на этот ответ с уточнением → бот видит reply,
поднимает прошлый Q+A, формирует промпт `Контекст:\n  Q: …\n  A: …\n\nНовый вопрос: …` и шлёт в
Codex. При reply на чужое сообщение / сообщение без записи в LRU — контекст не добавляется, работает
как обычно.

## Scope

Входит:

- Новый модуль `src/reply-context.mjs`: `remember(msgIds[], {question, answer})` создаёт один entry
  и регистрирует список msgId как алиасы на него; `recall(msgId)` возвращает entry или `null`. LRU
  по entries, фиксированный capacity (200 entries).
- Env `REPLY_CONTEXT_ENABLED` (default `false`) в `config.mjs` и `env.example`.
- В [src/bot.mjs](../src/bot.mjs): после успешного `sendAnswer` собрать список msgId (placeholder +
  все chunks) и сделать **один** `remember(msgIds, …)`. Плейсхолдер регистрируется только если он
  реально стал ответом (не остался текстом «Принял, думаю…» из-за fallback на `safeReply`).
- На входящем `message:text` с `ctx.message.reply_to_message?.from?.id === ctx.me.id` (через
  `bot.botInfo` после `bot.init()`) — делать `recall` и обогащать промпт. В групповых чатах с
  форум-тредами учитывать `message_thread_id` — entry per-thread.
- Усечение длины предыдущего ответа: `truncatePreservingSources(prevA, budget=2000)` — режет
  середину, оставляет начало и блок «Источники:» в хвосте, ставит маркер `…[обрезано]` в шов.
- Юнит-тест LRU + тест сборки промпта + тест на сохранение «Источники:» при обрезке.

Не входит:

- Многошаговый контекст (цепочка N reply-ов). Один уровень глубины — намеренно.
- Сохранение между рестартами.
- Передача контекста через `/start`-параметры или deep-links.
- Контекст для триаж-ответов (`MANUAL`/`DEEPPAVLOV` мимо Codex).

## Определение «готово»

- [ ] `REPLY_CONTEXT_ENABLED=true` включает фичу; `=false` (default) — бот работает stateless, как
      сейчас.
- [ ] Reply на ответ бота с текстом «расскажи подробнее» подтягивает прошлый Q+A в промпт.
- [ ] Reply на **любой** чанк длинного ответа подтягивает один и тот же entry (через `lookup`-map).
- [ ] Reply на сообщение, которого нет в LRU (после рестарта или вытеснения) — работает без
      контекста, без ошибок.
- [ ] Reply на не-бота (forwarded, цитата другого юзера, channel-репост через linked channel) —
      контекст не подтягивается.
- [ ] Контекст ограничен: предыдущий ответ обрезается до 2000 символов с маркером `…[обрезано]` **в
      середине**, начало и блок «Источники:» сохраняются.
- [ ] LRU считается по entries (не по msgId): при capacity=200 и пяти-чанковых ответах в памяти
      остаётся ровно 200 диалогов.
- [ ] Плейсхолдер «Принял, думаю…» не попадает в `recall` (регистрируем только если он стал
      финальным ответом).
- [ ] В форумных чатах `message_thread_id` — часть ключа entry, треды не путаются.
- [ ] `withReplyContext` обрамляет промпт **до** `withSystemPreamble` (или внутри неё — порядок
      зафиксирован в Фазе 3 и покрыт тестом).
- [ ] `npm run test:format`, новый `npm run test:reply-context`, `npm run ci:check` зелёные.

      отправителя того сообщения; `ctx.me.id` доступен после `bot.init()`, не лениво;
      `message_thread_id` (форумы) присутствует там, где есть. Если `ctx.me` не populated к моменту
      первого update — пробрасываем `await bot.init()` в bootstrap (`index.mjs`) до старта.
- [ ] Фаза 1. `src/config.mjs`:
      `replyContextEnabled = process.env.REPLY_CONTEXT_ENABLED === "true"`. Документировать в
      [env.example](../env.example) с пометкой про компромисс с `--ephemeral`.
- [ ] Фаза 2. `src/reply-context.mjs`: - `entries: Map<entryId, {question, answer}>` (insertion
      order = LRU). - `lookup: Map<msgKey, entryId>` где `msgKey = chatId:threadId:msgId` (threadId
      опционален). - `remember({chatId, threadId, msgIds}, entry)`: создаёт `entryId`, кладёт entry,
      регистрирует каждый msgId в `lookup` через тот же entryId. При переполнении (entries.size >
      capacity) — удалить самый старый entry **и все его записи в lookup**. -
      `recall({chatId, threadId, msgId})`: lookup → entryId → entry или `null`.
- [ ] Фаза 3. `src/prompt.mjs`: - `truncatePreservingSources(prevA, budget=2000)`: ищем последний
      блок `/(^|\n)Источники:[\s\S]+$/`, если есть — отрезаем сначала body до
      `budget - sources.length - "…[обрезано]\n".length`, потом подклеиваем sources обратно. Если
      блока «Источники:» нет — обычный slice + `…[обрезано]`. -
      `withReplyContext(prevQ, prevA, newQ)` — собирает строку
      `Контекст:\nQ: …\nA: …\n\nНовый вопрос: …` с обрезкой через `truncatePreservingSources`. -
      Порядок с `withSystemPreamble`: контекст подкладывается **внутрь** `withSystemPreamble` как
      часть «Вопрос:», т.е. вызов `withSystemPreamble(withReplyContext(prevQ, prevA, newQ))`.
      Закрепить тестом, иначе обёртки могут поменять местами и сломать формат.
- [ ] Фаза 4. В `src/bot.mjs`, в `bot.on("message:text", ...)`: - На входе: если
      `replyContextEnabled` и `reply.from?.id === ctx.me.id` и есть `recall` — обернуть промпт через
      `withReplyContext`. Иначе обычный путь. - На выходе после `sendAnswer`: собрать список msgId
      (`[placeholder?.message_id, ...chunkMsgIds]`, плейсхолдер включаем **только** если он стал
      финальным ответом — флаг `placeholderBecameAnswer`). Один `remember` для всего списка.
      `question` = исходный текст пользователя; `answer` = `result.answer` до `mdToTgHtml`. - Hit из
