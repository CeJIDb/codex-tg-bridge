# План: стриминг ответа в Telegram

**Дата**: 2026-05-22 **Задача**: показывать пользователю частичный ответ Codex по мере генерации,
редактируя placeholder вместо ожидания финала.

## Зачем именно так

Сейчас [src/codex.mjs](../src/codex.mjs) ждёт завершения процесса `codex exec`, после чего читает
`answer.txt` целиком. На запрос с `effort=medium` это 10–60 секунд молчания, в которые
[src/bot.mjs](../src/bot.mjs) держит сообщение «Принял, думаю…».

Важный нюанс по структуре времени запроса:

1. **Search-фаза (большая часть 10–60 сек):** агент читает `MANIFEST.md`, открывает файлы графа,
   вызывает tools. Текста ответа ещё нет — есть только события tool-вызовов в JSONL.
2. **Answer-фаза (последние секунды):** модель генерирует финальный текст — пачка дельт
   (`agent.message.delta` или аналог) приходит быстро.

Если стримить только дельты текста, placeholder будет молчать большую часть времени, а потом резко
наполнится за пару секунд — профит близок к нулю vs. текущее «Принял, думаю…». Поэтому реальная
ценность — **гибридный режим: стрим активности агента (имя tool, файл, который читается) во время
search-фазы, переход на дельты текста в answer-фазе**.

**Все гипотезы должны быть проверены в Фазе 0 до любого кода.** Фиксируем не только тип
delta-события, но и **все** типы событий в JSONL: `tool_call`, `tool_result`, `agent.message.delta`
и прочее, что окажется в выводе. Решение по режиму работы принимаем по артефакту:

- Есть и tool-события, и text-дельты → гибридный режим (приоритетный).
- Есть только tool-события → стрим активности, текст приходит финальным кадром (полезная фича).
- Есть только text-дельты → план в исходном виде (малый профит, но без регрессии).
- Полезных событий нет → degraded-режим: только AbortController + 429-handling, без собственно
  стрима.

Почему частые `editMessageText` не превратятся в спам уведомлений: Telegram **не пушит уведомление
на edit** — ни звук, ни баннер, ни счётчик непрочитанных. В чате просто всплывает обновлённое
сообщение с меткой «изменено». Один placeholder + N edits = 0 push'ей. Уведомление будет ровно одно
— на исходный `sendMessage("Принял, думаю…")`, плюс по одному на каждый дополнительный чанк
финального ответа (как и сейчас).

Альтернативы:

- Псевдо-стрим через taunt-сообщения «всё ещё думаю» — обманчиво, не даёт информации.
- Polling файла `answer.txt` — файл пишется только в конце, не подходит.
- **Парсинг JSONL стрима и инкрементальный `editMessageText` placeholder-сообщения** (гибридный
  режим: активность + текст). Естественный путь: если данные идут, прокидываем наверх и редактируем
  сообщение с тротлингом.

Ограничения Telegram, которые драйвят дизайн:

- `editMessageText` одного сообщения — не фиксированный rate, а флуд-контроль с растущим
  `retry_after` (секунды → десятки секунд). Поэтому 1500 мс — нижняя граница, а не гарантия. Любой
  429 уходит в обработчик с экспоненциальным бэк-оффом; на время cooldown intermediate-кадры
  дропаются, **финальный кадр ждёт окончания cooldown и всё равно отправляется**.
- HTML-парсер не любит обрезанные `**` и code-блоки → промежуточные кадры plain text, финальный —
  `mdToTgHtml` + линкификация.
- Накопительный буфер для JSONL: `stdout` отдаёт пачки байт, строка может прийти половинками. Парсер
  держит хвостовой буфер и режет только по `\n`.

Отмена: пользователь даёт `/cancel`, либо процесс получает SIGTERM. Стрим должен прерываться
немедленно: `codex` убивается через `AbortController`, callback дельт перестаёт срабатывать,
плейсхолдер фиксируется на «Отменено». Без этого `/cancel` будет редактировать «отменённое»
сообщение ещё десятки секунд.

## Цель

После `Принял, думаю…` placeholder постепенно наполняется текстом ответа по мере того, как Codex его
генерирует. Финальный кадр — отформатированный HTML с цитатами-ссылками, как сейчас. Никаких
регрессий по `linkifyCitations`, `mdToTgHtml`, `chunkByLines`.

## Scope

Входит:

- Разведка: запуск `codex exec --json` руками на типичных вопросах (короткий + длинный с несколькими
  tool-вызовами). Фиксация **всех** типов JSONL-событий в текущей версии CLI (0.130+), не только
  delta. Артефакты — `plans/data/codex-jsonl-sample.txt` и краткая таблица «тип события → несёт ли
  полезное содержимое для UI». На основании артефакта выбираем режим: гибридный (активность +
  текст), только-активность, только-текст или degraded.
- Рефакторинг [src/codex.mjs](../src/codex.mjs):
  `askCodexStream(prompt, { onDelta, onActivity, signal })`, возвращает
  `{answer, tokens, elapsedMs, model, effort}`. `onActivity({ kind, label })` для tool-событий
  (например, `{ kind: "read", label: "MANIFEST.md" }`), `onDelta(text)` для дельт ответа. `signal`
  пробрасывается в `execa` (через `cancelSignal`), при `abort()` процесс убивается, промис
  реджектится с `AbortError`. В degraded-режиме обе колбэка просто не вызываются.
- Накопительный stdout-буфер: режем строки только по `\n`, хвост держим до следующей пачки.
- Тротлер кадров в [src/bot.mjs](../src/bot.mjs) с обработкой 429: парсим
  `error.response.parameters.retry_after`, входим в cooldown, intermediate-кадры дропаем, финальный
  — ждёт и отправляется. Один тротлер на placeholder, в нём же — приоритет источника: если за
  последний интервал пришёл текст ответа, активность тулов в кадре игнорируется (текст важнее).
- Интеграция с `/cancel`: хранение `AbortController` активной задачи, `abort()` при cancel.
- Sanitize незакрытых markdown-конструкций в промежуточном кадре (или просто plain-text без HTML —
  предпочтительный вариант).
- Фолбэк-режим: если в Фазе 0 не нашли ни tool-событий, ни delta-событий — `askCodexStream` молча
  работает как `askCodex` (колбэки не вызываются), бот не показывает регрессию.
- Тест на тротлер (с `mock.timers` из `node:test`, без внешних libs), парсер дельт на
  зафиксированном куске JSONL, тест на abort.

Не входит:

- Стриминг сообщений между чанками (`chunkByLines`): финальный ответ разбиваем как раньше.
- Замена `--ephemeral` или режима sandbox.
- Прогресс-индикаторы (проценты, спиннеры).

## Определение «готово»

- [ ] При длинном ответе placeholder обновляется ≥ 3 раз за время выполнения (активность тулов и/или
      дельты текста — в зависимости от режима, выбранного по итогу Фазы 0) **либо** (если полезных
      событий не нашли) бот работает как сейчас без регрессий.
- [ ] Финальный кадр идентичен текущему поведению: `mdToTgHtml(linkifyCitations(text))`, чанки по
      `TELEGRAM_LIMIT`. Финал отправляется даже после 429-cooldown.
- [ ] При ошибке Codex placeholder получает текст ошибки, как сейчас (`safeEdit` fallback).
- [ ] Тротлинг: не более одного `editMessageText` в 1500 мс на сообщение **и** на 429 cooldown
      применяется экспоненциальный бэк-офф по `retry_after` (1, 2, 4, max 16 сек).
- [ ] `/cancel` во время стрима: процесс `codex` убит в ≤ 1 сек, плейсхолдер показывает «Отменено»,
      больше `editMessageText` по этому сообщению не уходит.
- [ ] Промежуточный текст plain (без HTML); финал — HTML; `linkifyCitations` применяется только в
      финале (известный UX-компромисс: голые `[РМРС-2-1 §4.3]` до финала, кликабельные — после).
- [ ] Накопительный stdout-буфер: тест на JSONL, разрезанный посередине строки (две пачки).
- [ ] Без регрессий: `npm run test:format`, `npm run test:triage`, `npm run ci:check` зелёные.
- [ ] Ручной smoke: задаю реальный вопрос, вижу постепенное заполнение **или** фолбэк без регрессий.

### Фаза 0: результаты разведки JSONL

Версия CLI: `codex-cli 0.130.0`. Запущено два кейса в `GRAPH_REPO_PATH`
(`marine-automation-requirements-graph`). Артефакт: `plans/data/codex-jsonl-sample.txt`.

#### Таблица типов событий

| Тип события                                        | Встретился          | Несёт tool-активность                              | Несёт дельту текста                         |
| -------------------------------------------------- | ------------------- | -------------------------------------------------- | ------------------------------------------- |
| `thread.started`                                   | да                  | нет                                                | нет                                         |
| `turn.started`                                     | да                  | нет                                                | нет                                         |
| `item.started`                                     | да (только с tools) | **да** — `item.command` содержит команду           | нет                                         |
| `item.completed` c `item.type="command_execution"` | да (только с tools) | **да** — `item.command` + `item.aggregated_output` | нет                                         |
| `item.completed` с `item.type="agent_message"`     | да                  | нет                                                | **текст целиком** в `item.text` (не дельта) |
| `turn.completed`                                   | да                  | нет                                                | нет (только `usage`)                        |
| `response.output_text.delta`                       | **нет**             | —                                                  | —                                           |
| `agent.message.delta` / любые иные дельты          | **нет**             | —                                                  | —                                           |

#### Режим работы: **только-активность**

`codex exec --json` версии 0.130.0 **не стримит дельты текста**. Финальный текст ответа приходит
одним блоком в `item.completed` с `item.type="agent_message"`. Streaming-дельт нет ни в коротком, ни
в длинном кейсах.

Tool-активность стримится через пары `item.started` / `item.completed` (тип `command_execution`). Во
время search-фазы (10–60 с) приходят десятки таких пар — это и есть полезный сигнал для индикации
прогресса в Telegram-плейсхолдере.

#### Контракт API

```js
// Контракт askCodexStream (src/codex.mjs)
askCodexStream(prompt, { onDelta, onActivity, signal });
// onDelta(text: string)                       — фрагмент текста ответа
// onActivity({ kind: string, label: string }) — событие активности агента
// signal: AbortSignal                         — для отмены через AbortController
// Returns: Promise<{answer, tokens, elapsedMs, model, effort}>
//
// Типы событий → колбэки (codex-cli 0.130.0, режим только-активность):
// item.started  (item.type="command_execution") → onActivity({ kind: "tool", label: item.command })
// item.completed (item.type="command_execution") → onActivity({ kind: "tool_done", label: item.command })
// item.completed (item.type="agent_message")    → onDelta(item.text)  [весь текст одним куском]
// turn.completed                                → resolve({ answer, tokens, elapsedMs, model, effort })
//
// Примечание: в текущей версии CLI onDelta вызывается ровно один раз с полным текстом,
// не пачкой дельт. Это ожидаемо для режима только-активность. Если будущие версии CLI
// добавят streaming-дельты — контракт расширяется без изменения сигнатуры.
//
// Фолбэк: если turn.completed не несёт текста (onDelta не был вызван) — читаем outFile
// как раньше. Это обратная совместимость с текущим askCodex.
```

### Фаза 1: реализация `askCodexStream`

Реализовано в двух файлах:

- `src/codex-parser.mjs` — изолированный модуль без зависимости от `config`: `makeJsonlParser`,
  `parseTokens`. Вынесен отдельно для юнит-тестирования без `.env`.
- `src/codex.mjs` — `askCodexStream` (новый) + `askCodex` (тонкая обёртка), реэкспортирует
  `makeJsonlParser`/`parseTokens`.

Тесты: `test/codex.test.mjs` — 9 тестов (3 suite), все зелёные:

- `makeJsonlParser`: onActivity на `item.started`, `tool_done` на
  `item.completed command_execution`, onDelta на `agent_message`, аккумуляция answer.
- накопительный буфер: разрез строки на два чанка, несколько строк в одном чанке, `flush()` для
  хвоста без `\n`.
- abort: `execa` с `cancelSignal` реджектит промис с `isCanceled=true`.

### Фазы 2–3: тротлер `createPlaceholderStream`

Реализован в `src/stream-throttle.mjs`. Изолированная state-машина с инжектируемым `editText` и
`now` (удобно для юнит-тестирования без реального Telegram). Ключевые решения:

- `pendingText` очищается только после успешного `editText` (snapshot-подход), при 429 — текст
  накапливается для следующего кадра.
- После освобождения `inFlight` вызывается `scheduleFlushIfNeeded()` — перепроверяет, не пришло ли
  что-то новое пока шёл предыдущий flush.
- `finalize()` ждёт окончания cooldown через реальный `setTimeout(resolve, remaining)` и
  принудительно отправляет финальный кадр.

Тесты: `test/stream-throttle.test.mjs` — 6 тестов, все зелёные:

- тротлинг ≥ 1500 мс (fake clock через инжектируемый `now`).
- приоритет текста над activity-строкой.
- abort → no-op для дальнейших колбэков.
- 429 cooldown: intermediate-кадр дропается, после cooldown проходит.
- экспоненциальный бэк-офф (1→2→4 сек при повторных 429).
- finalize ждёт cooldown и отправляет финальный кадр.
