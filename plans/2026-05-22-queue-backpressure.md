# План: живой backpressure в очереди

**Дата**: 2026-05-22 **Задача**: показывать ожидающему пользователю реальную позицию в очереди и её
изменение в реальном времени.

## Зачем именно так

Сейчас [src/bot.mjs:120-124](../src/bot.mjs) однократно сообщает `В очереди (N впереди)…` сразу
после `ctx.reply`. Дальше плейсхолдер замораживается до момента, когда задача стартует. При
`p-queue` с `concurrency=1` это значит: при двух-трёх параллельных вопросах пользователь видит «N
впереди» и больше ничего не происходит, пока его очередь не подойдёт. UX-ощущение — бот завис.

`p-queue` эмитит `active` (стартовала задача) и `next` (очередь сдвинулась). На каждом таком событии
можно пересчитать позицию каждой ожидающей задачи и обновить её плейсхолдер.

Альтернативы:

- Поллинг `queue.size` по таймеру — лишний шум, та же информация.
- Прогресс-индикатор «N % выполнено» — невозможно, у Codex нет прогресса.
- **Подписка на события очереди, edit плейсхолдера при смене позиции.** Минимальный и точный способ.

Ограничения Telegram, которые драйвят дизайн:

- `editMessageText` одного сообщения держит **примерно 1 правку в 3 секунды** до флуд-контроля (не
  задокументировано жёстко, эмпирика). Поэтому тротлинг — ≥ 3 сек на сообщение, а не 1 сек.
- `editMessageText` шлётся **только если позиция реально изменилась** — иначе сообщения дёргаются
  без причины и быстрее набегает флуд-контроль.
- Глобальный лимит на чат — 30 сообщений/сек. Фан-аут «Отменено по /cancel» на десятки ожидающих
  должен сериализоваться через rate-limit (бюджет 10 edit/сек, чтобы оставить запас остальному
  трафику).
- 429 на edit обрабатывается тем же бэк-оффом, что и в плане
  [streaming-answers](2026-05-22-streaming-answers.md): cooldown по `retry_after`, drop
  intermediate-обновлений позиции, финальный «выполняется/отменено» — обязательно.

Отмена и активная задача: `queue.clear()` убирает только ожидающих, но **активная задача продолжает
работать** и присылает ответ поверх «Отменено» соседям. Нужен `AbortController` активной задачи
(общий механизм с планом стриминга): `/cancel` вызывает `controller.abort()` + edit плейсхолдера
активного на «Отменено», и только потом `queue.clear()` для ожидающих.

## Цель

Пользователь, отправивший вопрос и попавший в очередь, видит, как его позиция уменьшается:
`в очереди: #3 → #2 → #1 → выполняется…`. При `cancel` ожидающие плейсхолдеры обновляются на
сообщение об отмене.

## Scope

Входит:

- Регистр ожидающих задач: `Map<taskId, { chatId, msgId, registeredAt, lastShownPos, lastEditAt }>`.
- Подписка на события `p-queue` (`active`, `next`, `error`).
- Тротлинг edit-ов: ≥ 3 сек на сообщение, edit **только при изменении позиции** против
  `lastShownPos`.
- Обработка 429 на edit: cooldown по `retry_after`, drop intermediate, финальный кадр гарантирован.
- `AbortController` активной задачи: `/cancel` сначала `abort()` активной, потом edit её
  плейсхолдера на «Отменено», потом — сериализованный фан-аут на ожидающих с rate 10 edit/сек.
- Юнит-тест на чистую функцию вычисления позиций по списку задач.

Не входит:

- Замена `p-queue` на другую реализацию очереди.
- Приоритеты, перестановка задач.
- Прогресс самой Codex-задачи (это покрывается планом стриминга).

## Определение «готово»

- [ ] При трёх одновременных вопросах второй и третий пользователи видят обновляющуюся позицию.
- [ ] При завершении активной задачи позиция следующих уменьшается на 1.
- [ ] `/cancel` сначала отменяет активную задачу через `AbortController`, потом edit-ит её
      плейсхолдер на «Отменено», потом редактирует плейсхолдеры всех ожидающих с rate 10 edit/сек.
- [ ] Активная задача (`queue.pending > 0`, моя позиция = 0) показывает «выполняется…» один раз и
      больше не дёргает `editMessageText`.
- [ ] Тротлинг: ≤ 1 edit/3 сек на одно сообщение **и** edit идёт только при реальной смене позиции
      против `lastShownPos`.
- [ ] 429 на edit обрабатывается через cooldown по `retry_after`, intermediate-кадры дропаются,
      финальный «отменено/выполняется» доедет (возможно с задержкой).
- [ ] При падении/таймауте активной задачи (`error` из `p-queue`) позиции остальных пересчитываются
      в той же handler-цепочке, что и `next`.
- [ ] Утечки `waiters` нет: запись удаляется в `finally` вокруг тела задачи **и** при провале
      сабмита плейсхолдера до `queue.add` (`try`/`catch`/`unregister`).
- [ ] При рестарте бот не пытается резюмировать старые плейсхолдеры (известный компромисс — см.
      «Зачем именно так»); UX-деградация документирована, не лечится в этом плане.
- [ ] `npm run ci:check` зелёный.

## Фазы и статус

- [x] Фаза 0. Прочитать API событий `p-queue` (`on('active', ...)`, `on('next', ...)`,

      — число активно выполняющихся. Зафиксировать порядок: после провала задачи сначала эмитится
      `error`, потом `next` (если так — recompute достаточно повесить на `next`; если нет — вешаем
      на оба).

      **Результат исследования** (`node_modules/p-queue/dist/index.js`):

      1. `queue.size` → `this.#queue.size` (строка 330) — число задач в очереди ожидания.
         `queue.pending` → `this.#pending` (строка 345) — число активно выполняющихся.
         Подтверждено.

      2. `'active'` эмитится в `#tryToStartAnother()` (строка 119) — непосредственно перед
         вызовом `job()`, то есть в момент старта задачи. `'next'` эмитится в `#next()` (строка
         70) — после `this.#pending--` и `#tryToStartAnother()`, то есть когда завершившаяся
         задача уже убрана из активных и очередь уже сдвинулась.

      3. Порядок при провале задачи (строки 234–244 в `add()`): в блоке `catch` сначала вызывается
         `reject(error)` и `this.emit('error', error)`, затем выполняется `finally { this.#next()
         }`, где `#next()` делает `this.#pending--`, запускает следующую задачу и только потом
         `this.emit('next')`.

      **Вывод:** `'error'` гарантированно эмитится **до** `'next'`. Значит, recompute достаточно
      повесить **только на `'next'`** — к моменту его срабатывания `pending` уже декрементирован,
      новая задача при наличии уже стартовала, и `'error'` уже доставлен. Подписка на `'error'`
      для пересчёта позиций **не нужна**.
